# Initiate New Project

## Quick Start

Use this skill to initialize a project with a small set of top-level entrypoints and deeper `docs/` layers. Prefer the deterministic scripts unless the user asks for a custom structure.

```bash
scripts/initiate_new_project.sh "/path/to/project"
scripts/validate_initiated_project.sh "/path/to/project"
```

## Workflow

1. Confirm the target project root from the user's request or current workspace.
2. Run [`scripts/initiate_new_project.sh`](scripts/initiate_new_project.sh) with the target project root.
3. Review the script report:
   - `Created:` files and directories added.
   - `Skipped existing:` files intentionally preserved.
   - `Generated:` files produced by managed scripts.
   - `Manual action required:` existing user scripts that were not executed.
4. Run [`scripts/validate_initiated_project.sh`](scripts/validate_initiated_project.sh) with the target project root.
5. If installing this skill locally, run [`scripts/install_local.sh`](scripts/install_local.sh) from the skill source directory.

## New Project Discovery Flow

After scaffolding, choose the clarification skill before writing durable project docs:

- Use `grill-me` for blank projects, early ideas, unclear users, fuzzy goals, or no source docs.
- Use `grill-with-docs` when the project already has `CONTEXT.md`, PRDs, ADRs, specs, source docs, legacy code, or domain notes.

Write distilled results to the project structure:

- Stable background, boundaries, terminology, and current facts -> `CONTEXT.md`.
- Product goals, users, scope, workflows, and requirements -> `docs/product-specs/`.
- Implementation plans and next steps -> `docs/exec-plans/active/YYYY-MM-DD-topic.md`.
- Design principles or experience decisions -> `docs/design-docs/`.
- Rejected approaches, technical debt, and deferred risks -> `docs/exec-plans/tech-debt-tracker.md`.

Do not preserve raw interview transcripts at the top level. Convert them into context, specs, plans, or design notes.

## Optional Version Control and Issue Handoff

After scaffolding and discovery, check development readiness only when the user intends to keep building the project.

- Detect whether the target is already inside a Git repository before suggesting version-control setup.
- If no Git repository exists, recommend Git initialization for long-lived code, product, collaboration, CI, release, or agent-driven development projects, but do not run `git init` without explicit user confirmation.
- If the user wants issue-driven development, first distill requirements into `docs/product-specs/` and `docs/exec-plans/active/`; then suggest `setup-matt-pocock-skills`, `to-prd`, or `to-issues` when those skills are available.
- If a GitHub remote or issue tracker exists, ask before creating external issues. If no tracker exists or the user has not confirmed publishing, keep issues and plans local under the docs tree.
- Never publish raw interview transcripts directly to issues. Publish only distilled, user-approved PRDs, specs, or implementation slices.

Do not automatically run Git, GitHub, or issue-tracker mutations from this skill. Require explicit confirmation before `git init`, `.gitignore` changes, branch or remote setup, `git add`, commit, tag, merge, rebase, push, GitHub repository creation, issue creation, label or milestone changes, project-board edits, or handoff skills that mutate collaboration state.

## Write Rules

- Create missing files and directories only.
- Never overwrite or append to existing `AGENTS.md`, `CONTEXT.md`, `DESIGN.md`, `FRONTEND.md`, `PLANS.md`, docs, or scripts.
- Treat existing scripts as user-owned unless they contain this skill's managed marker.
- Treat `docs/generated/project-directory.md` as user-owned unless it contains this skill's managed directory-index marker.
- Do not edit global Codex config or hook trust state.
- Keep generated templates generic; do not copy source workspace absolute paths into templates.

## Output Contract

The initialized project should contain:

```text
AGENTS.md
CONTEXT.md
DESIGN.md
FRONTEND.md
PLANS.md
docs/
  design-docs/
  exec-plans/
    active/
    completed/
  generated/
  product-specs/
  references/
scripts/
  update-project-directory.sh
  codex-project-directory-hook.sh
```

`docs/generated/project-directory.md` is generated by the managed directory-index script. It is refreshed only when missing or already marked as managed. `docs/generated/project-directory-hooks.md` explains optional hook wiring but does not modify global hook configuration.
